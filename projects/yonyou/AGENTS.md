# 新任务创建

用户明确要求在本机已有项目开启新 Codex 对话时，必须选择项目的 `environment: { type: "local" }`；除非用户明确要求，不默认创建工作树。

# 共用教材与教学方式

本项目以一套共同维护的章节教材组织教学。开始任何教学工作前，读取 `LEARNING-HUB.md` 和 `TEACHING-GUIDE.md`，并读取本模块的教材与进度。

- 教材源文件位于 `docs/`，通过 MkDocs 本地展示。用户先阅读对应章节，再在模块对话中提问。
- **开始一章教学前，必须先完成该章可阅读的正文、示例、常见误区和练习。** 大纲、聊天摘要、待补占位不算完整章节。
- 用户提问优先补充当前小节或章末答疑，答完明确回到哪一节；跨章内容记入模块进度中的“待后续解释”，除非用户明确要求深入，不擅自跳章。
- 每个模块只维护自己的 `docs/NN-*/` 和 `learning/NN-*/`。总对话维护首页、总纲、教学规则与站点配置；跨模块变更先交由总对话协调。
- 现有学习记录是事实依据。教材已写、用户已阅读、用户已掌握是不同状态，不得混记。
- 更新教材后，在共享虚拟环境可用时执行 `.venv-docs/bin/mkdocs build --strict` 检查，并链接具体教材章节。
- 不擅自更改 Skyler 项目，不自动创建对话或向其他对话发消息；如用户已授权特定协调动作，则在该范围内执行。

详细章节规范和模块路径见 `TEACHING-GUIDE.md`。

# 教学内容编写规范

以下内容是用户讨论后认可的教材编写要求，适用于所有模块的新增章节和后续修订。`TEACHING-GUIDE.md` 负责协作、目录与发布流程，`templates/CHAPTER-TEMPLATE.md` 提供章节骨架；内容质量以本规范为准。

## 1. 依据读者基础安排解释起点

- 学习者有计算机专业、SQL 和 AI 应用接触经历，使用 AI Coding 较多；代码理解与独立排障能力需要结合具体练习判断。
- ERP 业务、Linux、Docker 从基本用途和具体场景开始；Python 用短代码复习并按实际回答调整，不默认掌握项目已使用的框架。
- 不会 Java，不能把 Java 语法和生态作为默认前置。当前主线使用 Python，Java 深入学习按岗位实际要求调整。
- 编写前读取已有画像、当前章节和进度，明确可以使用的前置知识；不重复收集已经提供的信息。
- 例如 ERP 先讲员工怎样使用系统，再引入产品、模块、平台与接口；FastAPI 先建立请求与返回结果的认识，再引入路由、参数模型和依赖注入。

## 2. 每章围绕一个问题形成完整解释

- 开头写明本章解决的问题、必要前置、可观察的学习目标，以及后续再讲的范围；已有前置章节提供链接。
- 按完整理解划分章节，默认每章一个完整主题、每节一个主要问题，允许分几次阅读；不以字数或固定时间机械拆分。
- 解释概念之间的联系和中间步骤。术语清单、功能罗列、结论摘要、聊天转录或未完成的大纲不算完整教材。

## 3. 默认使用递进的讲解顺序

- 默认顺序：具体场景 → 核心概念 → 工作过程 → 完整示例 → 适用边界与异常。
- 先说明知识为什么有用，再解释它是什么、怎样工作和如何应用；可按内容调整顺序，但保持明确递进。
- API 可从“销售要查欠款，另一个程序需要向系统查询”展开，再讲请求与返回格式，最后区分客户不存在、无权限和查询失败。

## 4. 新术语及时解释，控制引入速度

- 首次出现术语时交代它属于什么、起什么作用，以及与已学概念的关系；英文和缩写作为补充。
- 不用一串未解释的术语解释另一个术语。若引入 Session、事务等必要概念，补充足以支持当前阅读的说明。
- 一个小节集中处理一个主要问题；需要大量额外知识才能理解时，增加前置小节，或移至明确标注的选读部分。

## 5. 示例连续、完整并可迁移

- 技术模块优先学习通用概念、执行过程与代码理解，不要求每章适配ERP。合成的“ERP 应收查询助手”可作为连续示例；主题适合时使用更简单的计算、天气、文件或资料查询等例子。业务细节按理解技术所需的最小范围交代，ERP产品与业务学习主要在00及后续场景实践中展开。
- 每个示例明确输入、处理过程、输出和必要假设。业务案例尤其说明金额、日期、状态和关联条件，不把模拟案例当作具体用友版本的实现。
- 适量加入其他场景，帮助理解知识如何迁移；不让例子和品牌名称喧宾夺主。

## 6. 代码逐步展开，解释关键变化

- 技术章节默认按“最小示例 → 解释执行过程 → 加入一个实际要求”推进。
- 每次扩展示例，说明原问题、修改位置、修改原因，以及输入、输出或执行路线的变化。
- 优先解释数据流、控制流和设计选择；复杂或用户卡住的部分再逐行拆解，不默认逐行翻译所有代码。
- 完整示例给出运行条件、必要依赖与版本、运行方式、预期输出和代表性错误；关键可运行代码应实际核对，并如实说明验证范围。
- 读代码练习可无需运行环境，须明确可先手动推演，不在开课前堆叠安装依赖。

## 7. 主动说明易混点与知识联系

- 用当前例子说明相关概念各自负责什么、怎样协作，避免错误对应。
- 典型易混点包括模型/SDK/Agent框架/Web框架，WebSocket/SSE/模型流式输出，订单额/应收/未收余额，SFT/LoRA/QLoRA。
- 表格用于职责或特征对照，流程图用于顺序与分支，正文说明原因；不为形式强行加入图表。

## 8. 区分核心理解、项目实践与深入原理

- 核心理解：概念、用途、基本机制和最小例子，属于主线，正文讲充分。
- 项目实践：接入、错误处理、排障和常见取舍，围绕当前任务展开。
- 深入原理：内部实现、性能机制和复杂变体，按需要设置并明确标为选读。
- 选读内容需有完整解释，不能只有名词和链接；不得将当前必需的解释全部隐藏到选读中。

## 9. 答疑回写正文，保持阅读主线

- 原文解释不足时补充相关正文或例子；常见共同疑问收录章末答疑并链接原小节。
- 跨章问题先给当前够用的解释，记录或链接后续内容；用户明确要求时可以深入，不自行因追问跳章。
- 事实或代码错误及时修正，并简要说明更正；不静默改变已经使用的练习题意。
- 同类答疑积累后整理并合并入正文，避免只追加问答使教材越来越散。
- 一轮答疑结束说明从哪里继续阅读；章节和小节标识尽量保持稳定。

## 10. 练习用于检查理解，用户掌握阅读进度

- 少量练习按需覆盖解释、推演、修改和排错，不要求每章机械凑齐所有类型。
- 折叠参考答案包含推理或判断依据；开放题允许多种合理实现。
- 用户可以先读、先问或直接做练习，不把答题通过作为继续阅读的强制门槛；用户主动要求推进时尊重其选择。
- 分开记录教材已准备、用户已阅读、已练习和已验证。未验证的知识如实标为待验证，不因看过答案或运行成功而认定掌握。

## 11. 来源与不确定性具体、适量

- 用友当前产品、接口、框架用法等优先核实官方资料，提供支持具体内容的直接链接；涉及版本和环境时交代适用条件。
- 区分通用知识、合成案例、公开能力和未确认的内部实际情况，不推测部门技术栈或客户部署。
- 限定说明放在必要位置并尽量集中，不反复插入相同声明打断讲解。

## 12. 发布前按阅读连贯性检查

- 前置是否交代，新术语是否解释，中间过程是否缺失，概念之间是否跳跃。
- 示例是否完整，关键代码、预期输出和业务假设是否一致。
- 重要结论是否说明原因与适用范围，图表、目录、链接和折叠内容是否正常。
- 读者能否说清本章学了什么，并知道当前阅读位置及下一步。

## 13. 根据反馈调整深度，适量补充 AI Coding 协作

以下补充依据用户于2026-11-07提出并修正的教学偏好：可以适当简化，保留原有教学主线。

适用范围：用户随后明确“第二章先保持这样，后续的要做好调整”。02模块保持当前内容与教学方式，继续按现有主线答疑，不因本次规范更新整体重写；以下调整用于后续课程，无需批量改写已有章节。

- 根据用户的实际理解和反馈动态调整讲解深度，熟悉的基础可以略过；帮助建立知识之间的联系，同时讲清当前任务必需的概念、核心机制和执行过程。
- 命令和代码先解释用途、关键语句或变化、执行顺序及预期结果，不以背诵全部语法和参数为目标；影响当前理解、实际排障或用户追问的细节再逐步展开。
- 适量加入向 AI 描述目标、上下文、约束和验收条件，以及检查其代码、命令、日志与运行结果的方法，作为概念讲解、示例和实际操作的补充；不把整套教材改成提示词、委托 AI 和验收模板。
- 完整正文、示例和练习保留供查阅；简化当轮讲解时，不删去理解当前内容所需的基础和中间步骤。
- 用户尚未记住语法不阻塞继续学习；通过解释、推演、修改和排错等具体证据判断理解，不把 AI 代为运行成功记成用户已经掌握。
- 用户要求一步一步时，每轮围绕当前一个小问题讲解，按反馈继续展开，并明确当前阅读位置。

## 默认章节结构

本章问题、目标与前置 → 具体场景 → 分节递进讲解 → 完整示例 → 易混点与排障 → 练习及折叠答案 → 本章回顾与检查清单 → 答疑、来源及后续链接。

按主题调整结构与篇幅，默认核心正文充分解释、深入原理选读；章节可以分次读，代码先讲执行过程与关键语句，必要处再逐行说明。学习者后续明确提出的偏好优先。
