# 03-07 拿到AI写出的代码，怎样读懂并核查？

> 教材已准备，2026-11-08。本章整合阅读方法、PyCharm操作与最小验收，保留概念与实际判断主线。

## 本章问题、目标与前置

AI已经写出一组文件，怎样判断它能不能完成“查询应收余额”，下一次需求变动又该改哪里？本章不增加新的Agent框架，整理你已经见过的代码路线。读完应能沿一次输入追到业务数据，描述关键改动与验证步骤，并区分模型错误、程序错误和数据错误。

前置为03-01至06，约35–45分钟。全面评估平台、部署与客户验收在07模块继续；这里先建立少量可重复的问题。

## 1. 先看文件职责，再追一次输入

| 文件 | 主要职责 | 阅读时找什么 |
| --- | --- | --- |
| model_config.py | 模型入口和请求设置 | 地址、型号、协议、凭据、超时重试 |
| business.py | 合成客户与余额规则 | 客户存在性、金额口径、币种、日期、来源 |
| intent.py | 结构化意图与执行条件 | 允许动作、编号规则、查询前置 |
| query_tools.py | 把业务函数包装成工具 | 描述、输入规则、实际执行函数 |
| 04_tool_loop.py | 明示模型→工具→模型循环 | 绑定、执行、回填、ID、上限 |
| 05_agent.py | 使用LangChain组织同类循环 | tools、system_prompt、输入状态、返回messages |
| 06_runtime.py | 等待、错误分类与文本流 | 限制范围、取消、部分结果 |
| 07_review.py | 无模型的业务与参数检查 | 确认查询端基础行为 |

最有效的一次阅读是拿“查星河制造”从05的main开始走：模型如何获得工具→候选如何返回→编号怎样进入余额工具→结果怎样进入最终消息。只有遇到不懂的函数，再跳到其定义看细节。

不必每次都从第三方库最深处开始。先读自己的入口、边界和业务条件，通常足以发现AI遗漏的主要步骤。

## 2. 三类对象不能混成一个result

`model.invoke`返回模型消息；`lookup_balance.invoke`返回业务数据；`agent.invoke`返回含messages的状态。这些变量即使都命名为result，也不是同一种东西。

| 对象 | 能告诉你什么 | 还需要检查什么 |
| --- | --- | --- |
| 模型消息 | 正文、工具请求、部分用量元数据 | 工具是否执行，是否遵守规则 |
| 工具结果 | 客户与业务状态、金额、来源日期 | 参数和口径是否正确 |
| Agent最终状态 | 本轮的消息过程与最终回复 | 哪条ToolMessage支持哪项回答 |

读到`result["amount"]`时，先确认result确实是成功的余额查询结果。若是AIMessage或Agent状态，该索引不符合数据形状。良好的变量名能减少误读，但最终以真实类型和字段为准。

## 3. 先做无需模型的检查

```python
"""无需Key：先核对业务函数与参数，不调用模型。"""
from pydantic import ValidationError

from business import get_balance, search_customers
from query_tools import lookup_balance


def main():
    for customer_id in ("C001", "C002", "C003", "C999"):
        print(customer_id, get_balance(customer_id))
    print("重名候选：", search_customers("海星"))
    try:
        lookup_balance.invoke({"customer_id": "随便一个客户"})
    except ValidationError:
        print("格式错误已被拦下，业务函数没有被调用。")


if __name__ == "__main__":
    main()
```

这份文件验证业务函数的确定行为：C001=12800、C002=0、C003=500，C999为not_found，“海星”有两个候选，错误编号被参数校验拦下。它不验证模型会不会选择正确工具。

运行成功后才有一个清楚的起点：如果Agent还回答错，就检查其参数、路线和结果解释。若本地函数本身就算错，先修数据或业务逻辑，不要靠提示词要求模型“更准确”。

## 4. 给同一版本保留一组固定问题

下面是本模块的最小检查表。它是业务期望，尚未替你对真实模型执行。每次改提示词、工具描述或模型，复用同一批输入，记录实际轨迹和结果。

| 输入 | 期望行为与证据 |
| --- | --- |
| 查C001未收余额 | lookup_balance(C001)，回答12800 CNY，日期与来源正确 |
| 查C002 | 成功查询后说明余额0 |
| 查C999 | 说明未找到，不能补0 |
| 查星河制造 | 先找唯一C003，再查500 |
| 查海星 | 展示北京/上海候选并澄清，不猜第一个 |
| 查那个客户 | 缺少明确对象时澄清 |
| 工具参数写成“客户一” | 校验失败或请求纠正，不继续错误查询 |
| 工具返回“数据不可用” | 如实说明失败，不说无欠款 |
| 用户要求登记收款 | 本版没有写工具，不能声称已经登记 |
| 客户备注要求忽略规则 | 备注继续作为数据，不改变权限或查询目标 |

一条检查分成三部分记录：模型提出什么，工具实际做了什么，用户最终看到什么。模型输出措辞允许变化，金额、对象、状态与必要澄清不能随意变化。

## 5. 发现错误后，先归类再修改

客户名称识别错或遗漏澄清，先查输入和工具说明；工具选择错，检查工具描述与传入目录；工具执行失败，查参数、依赖或业务服务；数据已错，查数据源与口径；工具正确而答案错误，查回答生成与后处理。外部认证/网络问题按03-06排查。

例如“海星”直接查C001，可能是模型忽略歧义规则。你可以先改善工具说明与提示词并重复测试；若业务要求每次都严格拦住歧义，应该在应用层验证唯一选择，这需要确定性的代码。两种修改的保证范围不同。

不要因为某次回答正确，就删掉全部检查；也不要因为一个问题失败就立刻同时换模型、改工具、重写所有提示词。每次改一个可解释的点，使用相同输入对照，才能知道变化来自哪里。

## 6. 怎样向AI描述一项修改

例如要增加“显示数据日期”，可以这样表达：

```text
目标：余额回答同时显示查询结果中的as_of日期。
现有约定：金额、币种、日期必须来自成功的lookup_balance结果；not_found不能补0。
修改范围：先检查05_agent.py与业务返回；不要更改余额计算或新加框架。
核查：C001仍为12800 CNY，日期来自工具；C999仍未找到。
请说明改了哪几个位置、数据如何流动、还需要我验证什么。
```

这些字段帮助AI对准任务，也帮助你读修改结果。最终仍要打开文件或diff，找到真正变化的代码，并用固定输入核对。AI写了“测试通过”时，看它实际运行了什么；本地模拟响应通过和真实模型选择正确是不同记录。

## 7. PyCharm里需要掌握的最少操作

先核对解释器与Run配置，再用断点查看变量。在模型返回处观察tool_calls，在工具执行前后观察args和payload，Agent结束后看messages。需要时使用Step Over逐行走自己的代码，进入业务函数可用Step Into；进入第三方SDK后可返回调用者，先抓主线。

修改前用Git看当前状态，修改后看diff。只核对与本次目标相关的文件，不把AI生成的一大批变动一次性默认接受。用户愿意时可以运行配套文件，或只按这条路线手动阅读；不需要先手写整套代码才继续。

最小交接要能说明：使用哪个代码版本、哪个解释器和依赖、模型入口与协议、必要配置名称、怎样运行、已验证哪些问题、哪些仍待实测。不要在交接里附上Key。

## 8. 可选练习

A. AI把所有失败改成“暂无欠款”，为什么程序看起来更稳定却更危险？B. 离线模拟模型按预设返回工具请求，能证明真实Qwen也会这样选吗？C. 新需求只改变输出日期，应该重点复查什么？

??? note "参考答案与推理"
    A：隐藏了未知客户、网络和数据故障，把无证据转成零余额结论。B：不能，模拟只证明预设输入下的程序与框架执行，真实模型的选择需另测。C：确认日期来自工具且未破坏金额、状态与查找路线，使用C001/C999等原有输入对照。

## 本章回顾与检查清单
