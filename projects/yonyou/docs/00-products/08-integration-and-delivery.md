# 00-08 ERP AI 场景的数据接入与交付

> 教材已准备，实际阅读与练习单独记录。更新及官方资料核对日期：2026-10-19。

## 本章问题、目标与前置

**客户说“我们用用友，想做一个欠款查询助手”，怎样把它变成可以接入、核对和验收的工作？**

前置是 [第 5 章的余额与逾期口径](05-receivables-to-cash.md#due-and-overdue)和 [第 7 章的能力分工](07-ai-and-product-map.md#tools-and-execution)。本章不重复业务概念，直接整理一次交付所需的决定和证据。约 25–30 分钟，可以按需求、接入、验收三段阅读。

读完应能写出一份小型场景说明，选择合适数据入口，核对接口字段的业务含义，并用具体案例判断结果是否正确。本文产物是**合成场景的接入与验收说明**，没有连接真实客户系统；工程实现、部署与模型评测由相应技术模块继续完成。

## 1. 先把一句要求变成一页场景说明 {#scenario-spec}

客户最初说：“希望销售能直接问客户欠多少钱。”这句话还没有确定“欠款”是什么数字、数据从哪里来、谁能看，以及怎样判断做对了。

以本课程的应收助手为例，先把结果写具体：

| 项目 | 本教学场景的决定 |
| --- | --- |
| 使用者与任务 | 已登录销售查询授权公司、客户的当前应收情况 |
| 输入 | 当前公司、明确的客户、查询日期；公司可来自当前选择，客户可由名称解析 |
| 核心结果 | 逐笔及合计未结清应收、按当前记录的逾期未结清、同客户待匹配收款 |
| 解释依据 | 应收/收款编号、到期日、数据时点和采用的口径 |
| 数据范围 | 同一授权公司、客户和币种；教学例为 ORG-SH、C001、人民币 |
| 时间范围 | 第一版提供当前快照，不支持还原任意历史日期 |
| 处理动作 | 只读查询；可说明下一步，当前场景不修改核销或发送催收消息 |
| 成功标准 | 样例金额、范围、来源与约定一致；异常能明确反馈 |

这份说明使业务人员能检查结果，工程人员也知道要找哪些能力。真实项目开始时，把客户实际产品、版本、环境、业务负责人、数据与接口负责人填到同一份说明里。“用友”这个名称本身还不足以决定文档和接入入口。

遇到“欠款”这种口头表达，可以把期望输出示例给业务人员确认：是看逐笔未结清、客户资金净差额，还是可直接催收的金额？先确认这个决定，比先写一段很长的提示词更能避免口径偏差。

## 2. 选择现有数据入口 {#data-entry}

ERP 页面能查到数据，是确定来源的一条线索。下一步应核实该环境能为程序提供什么入口。

| 已有条件 | 可考虑的入口 | 接入前要核实什么 |
| --- | --- | --- |
| 业务 API 已开放所需查询 | 调用对应产品和版本的业务接口 | 授权、参数、组织、返回字段、分页、错误和数据时点 |
| 已有统一应收报表或数据服务 | 使用已定义的查询服务/数据集 | 金额口径、覆盖范围、更新时间、权限和来源明细 |
| 项目允许读取数据库或视图 | 使用获授权的只读视图或受控查询服务 | 表/视图含义、有效性、定制字段及权限怎样实施 |
| 暂时只有人工导出文件 | 用固定样例或导出快照做原型 | 明确导出范围与时点；文件更新前不称为实时结果 |

优先使用已经满足需求的入口。一个服务能直接返回逐笔余额，就不必为了模仿教材重新拆出多张表再算一次；如果服务只给客户总额，而验收要求定位到某笔应收，就还需要明细来源。

用友开发者中心公开提供 OpenAPI 业务服务、授权和接入资料；U8 的 API 中心另有应收、收款等资源列表。它们说明存在产品级入口，实际应使用客户匹配的产品文档和环境，不把 U8 的路径套到 YonSuite。[用友 OpenAPI](https://developer.yonyou.com/openAPI)、[U8 API 中心](https://u8open.yonyou.com/apiCenter/index)

### 2.1 先跑通一次小范围查询

选定入口后，先使用一位已授权用户、一个公司、一个客户，与业务人员认可的报表核对。对照的是同一时点、范围和口径，而不是拿今天的 API 结果与昨天导出的另一种报表比数值。

若不一致，先定位是少页、组织过滤、状态、金额定义、更新时间还是调整记录造成的。此时需要修正数据映射或查询，不急于通过改回答措辞掩盖差异。

## 3. 完整样例：入口给什么，助手回答什么 {#example-data}

现在假设已经选到一个获授权的查询服务。它返回下面的当前快照，沿用第 5 章原始数据，**没有叠加第 6 章的退货分支**。

**`query_context`：本次成功查询的上下文。**

| 字段 | 本例值 |
| --- | --- |
| request_id（查询请求编号） | Q-101 |
| organization_id（公司） | ORG-SH |
| customer_id（客户） | C001 |
| currency（币种） | CNY |
| query_date（查询日） | 2026-10-19 |
| snapshot_at（业务快照时点） | 2026-10-19 10:00，Asia/Shanghai |
| fetched_at（取得快照时间） | 2026-10-19 10:01，Asia/Shanghai |
| status（查询结果） | OK |
| complete（范围内数据是否完整） | true |

**`ar_balance_view`：已经核销后的逐笔应收余额，不需要再减收款。**

| ar_id（应收单） | source_order_id（来源订单） | original_amount（原应收/元） | allocated_amount（已匹配/元） | open_amount（未结清/元） | due_date（到期日） |
| --- | --- | ---: | ---: | ---: | --- |
| AR101 | SO101 | 10,000 | 4,000 | 6,000 | 2026-10-18 |
| AR105 | SO105 | 2,000 | 1,000 | 1,000 | 2026-10-25 |

**`receipt_balance_view`：实收及尚未匹配金额。**

| receipt_id（收款单） | receipt_date（到账日） | received_amount（实收/元） | allocated_amount（已分配/元） | unallocated_amount（待匹配/元） |
| --- | --- | ---: | ---: | ---: |
| RC201 | 2026-10-17 | 5,000 | 5,000 | 0 |
| RC202 | 2026-10-18 | 1,000 | 0 | 1,000 |

### 3.1 处理过程

本例的上下文已明确公司、客户、币种，记录均确认有效，无其他调整，查询日超过到期日才算逾期。服务已将第 5 章的匹配关系处理到余额中，助手使用这些**已定义的余额字段**：

```text
未结清合计：6,000 + 1,000 = 7,000 元
按当前记录逾期未结清：AR101 的 6,000 元
待匹配收款合计：0 + 1,000 = 1,000 元
```

金额汇总和日期比较可由查询服务或确定的程序计算，模型负责理解问题与呈现结果。这样能直接检查计算过程，不依赖模型在长文本里自行猜字段或反复算账。

### 3.2 输出示例

> 数据截至 2026-10-19 10:00，上海公司 C001 的人民币未结清应收合计为 7,000 元：AR101 为 6,000 元，AR105 为 1,000 元。其中 AR101 到期日为 10 月 18 日，按当前核销记录逾期未结清 6,000 元。另有 RC202 的 1,000 元已到账待匹配，逐笔待催金额需先核实该款用途。来源：AR101、AR105、RC201、RC202；查询编号 Q-101。

这里显示的是业务快照时间 10:00。10:01 是取得这份快照的时间，不能将其写成“数据已更新到 10:01”。如果员工需要刚完成的核销结果，就要重新取得满足要求的新快照。

## 4. 给数据入口约定清楚的输入与返回 {#service-contract}

**服务约定**就是调用方与提供方共同明确“传入什么、返回什么、出错怎样表达”。本章给业务层面的约定，不限定 HTTP 路径或编程框架。

### 4.1 输入与授权

| 输入或上下文 | 本例要求 |
| --- | --- |
| 员工身份 | 由登录系统或可信服务取得，再由后端检查数据授权 |
| 公司、客户 | 用已经确认的标识；名称不唯一时，先返回候选供选择 |
| 日期 | 当前查询日期；不支持历史时明确反馈 |
| 币种 | 本例仅汇总人民币；多币种结果分开或使用另外确认的折算规则 |

身份、公司和客户如何识别已在 [第 2 章](02-business-objects.md#ai-query-context)说明。这里要落实的是：用户输入的公司必须通过后端授权检查，不能仅靠提示词限制模型。

### 4.2 返回结果需要包含什么

| 返回类别 | 本场景需要的内容 | 为什么需要 |
| --- | --- | --- |
| 执行结果 | 成功、无权限、服务不可用等明确状态 | 区分有效数字与未取得结果 |
| 范围与时点 | 公司、客户、币种、快照时间 | 检查是否回答了本次问题 |
| 业务结果 | 应收余额、到期日、待匹配款、来源编号 | 支持金额与解释核对 |
| 完整性 | 是否全部取得；若分页，如何确认已取完 | 防止把一页当成客户总额 |
| 定位信息 | 查询编号及可追查的来源 | 业务人员核对、工程人员查失败时有共同入口 |

`complete` 等字段名是本教材的服务约定，真实接口也可以通过总条数、末页标志或其他方式表达。重点是调用方能够确认完整性，不能假设每个产品都返回相同字段。

### 4.3 核对真实字段时看业务定义

| 发现的字段或结果 | 需要确认的问题 |
| --- | --- |
| `balance` | 是原应收、未结清，还是包含待匹配款的客户净额？ |
| `amount` | 对应哪种金额，币种和单位是什么？ |
| `status` | 表示审核、有效性、核销进度还是接口执行结果？ |
| 只有订单金额 | 是否还缺应收和结算数据，当前入口能否满足需求？ |

把确认后的字段映射写在场景说明旁。模型、接口调用方和验收人员使用同一套定义，后续版本变化时才能知道要改哪一处。

## 5. 成功、空结果与未完成怎样表达 {#failure-handling}

| 实际情况 | 本场景的反馈 |
| --- | --- |
| 查询成功，已确认客户存在、范围完整，应收与待匹配款都为空 | 当前口径下没有未结清应收或待匹配款，可显示合计 0 |
| 未能确定客户，或客户不存在 | 反馈对象未确定/未找到，不返回“余额 0” |
| 无权查询所选公司 | 反馈该范围无查询权限，不披露受限金额 |
| 服务超时或返回错误 | 反馈暂未取得结果，保留查询编号用于定位 |
| 只拿到部分页面 | 继续取得剩余页面；未完成前不把部分合计标成完整总额 |
| 应收余额有值，但某笔到期日缺失 | 可报告已取得的余额；注明该笔到期情况无法判断 |
| 只提供当前快照，却要求历史余额 | 反馈当前入口不支持历史还原，另找历史数据来源 |

数据不全时仍可展示明确标注的已取得部分，但要让员工知道还缺什么，以及哪个问题尚未回答。错误处理也是业务结果的一部分。

### 5.1 后续扩展到创建任务时

如果以后增加“创建内部对账任务草稿”，单独补充对象、负责人、授权、成功编号与失败反馈，不把“查询成功”视为“任务已创建”。

调用方为同一次创建保存一个唯一请求编号。服务若支持按该编号去重或查处理结果，重试时沿用它；这种重复请求不会重复创建的性质称为**幂等**。服务不支持时，超时后应先核实业务结果再决定重试，不能盲目再建一份。此处是接入前需要确认的行为，不假定真实产品已经具有某个去重字段。

## 6. 用样例定义验收 {#acceptance-cases}

**验收**是在约定条件下检查结果是否符合需求。先把预期写出来，再执行，能避免只看演示是否流畅。

下面案例独立执行，均从 §3 基准数据开始，除“变化条件”外其他条件不变。用户 U001 仅有 ORG-SH 的查询权限。客户资料中，C001 全称“上海星海科技有限公司”、C002 全称“杭州星海设备有限公司”，简称均为“星海”。C000 是已确认存在且获授权的另一客户。

| 编号 | 输入或变化条件 | 预期结果 |
| --- | --- | --- |
| T01 | 查询 ORG-SH、C001 的当前应收 | 未结清 7,000；当前记录逾期未结清 6,000；待匹配 1,000；显示快照时点和来源，不直接确定逐笔待催金额 |
| T02 | 仅说“查星海”，尚无选中客户 | 给出两个候选供确认，不把 C001、C002 金额混算 |
| T03 | U001 要查 ORG-BJ 的 C001 | 返回范围无权限，不返回受限金额或将其填为 0 |
| T04 | 查询服务超时，没有取得快照 | 明确查询未完成，不生成一个看起来合理的金额 |
| T05 | 分页尚未取完，完整性为 false | 不输出完整客户合计；继续取数或反馈仍不完整 |
| T06 | 查询 C000 成功、范围完整，应收和待匹配款均为空 | 可以报告当前口径下两类合计均为 0 |
| T07 | 仅把 AR101 的到期日改为缺失 | 未结清仍为 7,000，待匹配仍为 1,000；AR101 无法判断是否逾期，不宣称已得到客户完整逾期金额 |
| T08 | 要求还原 2026-10-01 当时余额，入口仅有当前快照 | 说明历史查询暂不支持，不用今天的余额代替 |

T01 的金额可以与固定样例逐项比较。T02–T08 则需要检查输出行为，例如是否泄露范围外数据、是否把失败说成 0、是否误用时间口径。业务负责人核对结果含义，工程人员结合相同查询编号检查执行过程。

这些是验收案例和预期，不代表真实接口已经跑通。原型可以先用固定输入输出验证；接入真实环境后，还需在匹配环境执行并记录实际结果。

## 7. 交付时留下什么 {#delivery-artifacts}

对于这个小场景，一份可交接的结果至少能回答下面几件事：

| 交付内容 | 本例应包含什么 |
| --- | --- |
| 场景与口径 | §1 的输入、输出、范围和当前快照约定 |
| 接入与字段映射 | 实际产品/版本、入口说明、余额字段含义、授权和更新时间；凭据使用既有安全配置，不写入教材或报告 |
| 验证记录 | 对照报表及其时点、T01–T08 的实际结果和未解决项 |
| 使用与维护说明 | 入口位置、怎样看来源、失败时找谁、配置或制度变化后怎样更新 |

范围按当前需求安排。若数据入口已经提供正确的核销余额，本次交付重点就在接入、解释与核对；若缺少必要字段，就先把差距和补充方式写清。没有必要为了“完整系统”重复实现客户已经有的业务功能。

## 8. 练习：检查一份交付结果 {#practice}

### 练习 1：输出里哪些地方有问题

下面就是全部解题数据，人民币，ORG-SH 的 C001，用户已获授权，当前查询成功且完整。到期日当天不算逾期，没有其他调整，服务返回的是核销后的余额。

**`query_context`：查询时点。**

| query_date（查询日） | snapshot_at（业务快照） | fetched_at（取得时间） |
| --- | --- | --- |
| 2026-10-19 | 2026-10-19 10:00 | 2026-10-19 10:01 |

**`ar_balance_view`：逐笔应收。**

| ar_id（应收单） | original_amount（原应收/元） | allocated_amount（已匹配/元） | open_amount（未结清/元） | due_date（到期日） |
| --- | ---: | ---: | ---: | --- |
| AR101 | 10,000 | 4,000 | 6,000 | 2026-10-18 |
| AR105 | 2,000 | 1,000 | 1,000 | 2026-10-25 |

**`receipt_balance_view`：待匹配收款。**

| receipt_id（收款单） | unallocated_amount（待匹配/元） |
| --- | ---: |
| RC202 | 1,000 |

助手回答：“数据更新到 10:01。AR101 还欠 2,000 元，因为余额 6,000 元再扣已匹配的 4,000 元。整个客户全部逾期，现在应催收 3,000 元。”

指出主要错误，并写一个正确的简短结果。

??? note "参考答案 1"
    业务快照是 10:00，10:01 只是取得时间。AR101 的 6,000 元已是核销后的余额，不能再扣 4,000 元。AR105 的到期日为 10 月 25 日，并未逾期。RC202 的 1,000 元尚未匹配，不应直接得出逐笔待催金额。

    正确结果可写：“数据截至 2026-10-19 10:00，C001 未结清应收 7,000 元，其中 AR101 的 6,000 元按当前记录已过到期日；AR105 的 1,000 元未到期。另有 RC202 的 1,000 元待匹配，需核实用途后确定逐笔待催金额。”

### 练习 2：哪些情况可以回答 0

以下为四次相互独立的查询，范围均已明确。没有其他已知数据；请仅按结果判断，不推测金额。

**`query_result_cases`：服务实际返回。**

| case_id（案例） | status（结果） | customer_exists（客户存在） | complete（数据完整） | 返回内容 |
| --- | --- | --- | --- | --- |
| A | OK | true | true | 应收与待匹配款均为空 |
| B | NO_ACCESS | 未披露 | false | 无业务数据 |
| C | UNAVAILABLE | 未取得 | false | 请求超时 |
| D | OK | true | false | 仅取得第一页，未结清小计 0 |

本场景约定：只有成功、已确认对象存在且数据完整，才能把空结果解释为当前口径下的 0。哪些可以回答合计 0，其余分别怎样反馈？

??? note "参考答案 2"
    只有 A 可以报告两类合计均为 0。B 反馈无权限；C 反馈尚未取得结果；D 继续取数或说明数据不完整，不能把第一页小计当成客户总额。

    验收应分别覆盖这些情况，因为相同的“没有显示金额”可能来自不同执行结果。
