## 02 异步｜05

- 等待时让其他任务有机会执行：先分清当前任务与其他任务
  - 说明：对应 05 章。示例假设工作主要耗时在可让出的等待上。短字典取值无需套线程；同步阻塞 I/O 可按需使用 asyncio.to_thread，但那会实际用到线程。
  - ① async：定义一种可等待的工作
    - 教材：http://127.0.0.1:8765/01-python-api/05-async-and-tasks.html
    - async def 定义协程函数
    - 调用 f() 通常先得到协程对象，函数体尚未执行
    - await f() 或安排为任务，才能推进这项工作
  - ② await：本任务等结果
    - 说明：await 只能等待可等待对象。若操作已经完成，await 可以直接继续，不保证每次都切换。await 不会自行创建另一项工作，也不会让当前任务跳过等待去执行下一行。
    - 操作尚未完成时，当前任务暂停
    - 事件循环可安排其他已就绪的任务
    - 完成后，本任务恢复并执行 await 后面的语句
  - ③ asyncio：运行和安排这些工作
    - 事件循环：安排就绪任务继续执行
      - 本例在一个线程中交替推进多个任务
      - 多核并行要用其他机制；本例未使用
    - asyncio.run(main())
      - 脚本入口创建事件循环，运行并收尾
      - FastAPI 异步路由里已有循环，直接 await 即可
    - asyncio.sleep(1)
      - 模拟等网络回复；不阻塞事件循环
      - time.sleep(1) 在循环线程里会阻塞其他任务
  - ④ 顺序与并发：看怎样安排
    - 顺序：await A(); await B()
      - B 在 A 完成后才开始
      - A 等 2 秒，B 等 1 秒 → 约 3 秒
    - 并发：await gather(A(), B())
      - 两项被安排执行，等待可重叠
      - 同样两项 → 约 2 秒，另有少量开销
    - create_task(A())：持有任务对象
      - 先安排 A，当前任务可继续安排 B
      - 需要结果时 await task；也可通过 task 请求取消
    - gather 的结果次序
      - 说明：默认某项失败时，gather 可先传播异常，不自动取消其他仍在执行的项。不能把 gather 概括成任何情况下都等全部结束。
      - 全部成功时，等齐结果再返回列表
      - 按传入顺序排列；B 先完成也不自动排第一
  - ⑤ 正常、失败、超时、取消
    - 正常完成 → 返回值；执行失败 → 异常
    - wait_for(work(), timeout=...)
      - 到时会请求取消所等待的工作
      - 等待其响应取消后，本例向调用者抛 TimeoutError
    - task.cancel() → 请求取消
      - 再 await task，等待其响应与收尾
      - 通常在等待处收到 CancelledError；它不属于 Exception
    - 取消客户端的等待，不保证远端服务器同步停止
  - ⑥ 回到实际查询
    - 教材：http://127.0.0.1:8765/01-python-api/00-one-example.html#extensions
    - client.py [C1] 的 await：等 HTTP 响应
    - server.py [S3] 的 await：模拟服务端等待
    - client.py [C4/C5]：并发、超时与取消

- 两个程序怎样交换一次查询：HTTP 是规则，JSON 是数据格式

  - ① 谁发起、谁处理
    - 说明：客户端和服务端是本次通信里的角色，可以运行在同一台电脑，也可以在不同电脑。浏览器并不是唯一的客户端。
    - 客户端：主动发出请求，使用结果
    - 服务端：接收请求，处理并回复
    - 同一程序访问上游时，也可以成为客户端
  - ② 找到服务，再找到功能
    - 教材：http://127.0.0.1:8765/01-python-api/06-http-and-json.html
    - http://127.0.0.1:8010/receivables/query
      - http：通信协议；127.0.0.1：本机地址
      - 8010：服务监听端口；/receivables/query：功能路径
    - 同一端口可提供很多路径；只找对端口还不够
    - ?delay=0.4：URL 查询参数，本例只用于模拟等待
  - ③ 请求：我需要你做什么
    - 方法：例如 GET 查询、POST 提交请求数据
    - 路径参数：/customers/C001 中的 C001
    - 查询参数：?min_amount=1000
    - 请求头：Content-Type 说明请求体格式
    - 请求体：例如 {"customer_id":"C001","min_amount":null}
  - ④ 响应：处理结果是什么
    - 状态码：200 成功；404 未找到；422 输入不符合约定
    - 响应头：说明内容类型等信息
    - 响应体：例如 {"customer_id":"C001","amount":12800}

  - ⑤ JSON 与 Python 数据怎样转换
    - dict → str → bytes

    - str / bytes → Python 数据
      - json.loads(payload)：解析 JSON
      - JSON 对象 → dict；数组 → list；null → None
    - 这些转换函数本身没有发送网络请求
    - type(result) → <class 'dict'>；type(result).__name__ → dict
  - ⑥ 一次真实往返
    - 说明：双方不会跨网络共享同一个 Python 字典对象。网络收发由 HTTP 客户端与服务器软件等配合完成；JSON 只规定数据表示。

    - 客户端字典 → 编码 JSON → HTTP 请求
    - 服务端解析、校验 → 查业务数据 → HTTP 响应
    - 客户端解析 JSON → 自己程序中的新数据

## 05 持续通信｜09–10

- 一次完整结果，还是持续交互：按需要选择返回方式
  - 说明：对应 09–10 章。SSE 的事件流主要是服务端向客户端发送，客户端仍可另外发送 HTTP 请求。WebSocket 通常通过 HTTP 握手建立，随后按 WebSocket 消息通信；不是 HTTPX 的一种写法。
  - 普通 HTTP：一次查询，一次完整结果
    - 例如：查 C001 → 收到金额 12800
    - 适合本次需求只要一个完整结果
    - HTTP 连接可以复用；不等于每次响应后都断开 TCP
  - 09 流式与 SSE：逐步把内容交出来
    - 教材：http://127.0.0.1:8765/01-python-api/09-streaming-and-sse.html
    - yield：每次交出一项，保留后续执行位置
      - return：结束函数，交回最终结果
      - async for：逐项读取异步产生的内容
    - StreamingResponse：逐块产生响应内容
      - 数据在同一次 HTTP 响应中逐步到达
      - SSE 是一种有明确事件格式的流式响应
    - SSE 事件格式
      - Content-Type: text/event-stream
      - event: progress → 事件名；data: ... → 内容
      - 空行结束一条事件；本例 data 内再使用 JSON
    - 本例：一批查询的进度与结果
      - progress → result / failed → 下一项 → done
      - C999 失败用 failed 事件表达，之后仍查询 C002
    - 结束与断开
      - 本例 done 后客户端主动 close，避免自动重连重复查询
      - 服务端 finally 清理；断开时管理自己启动的后台任务
  - 10 WebSocket：同一连接反复双向发消息
    - 教材：http://127.0.0.1:8765/01-python-api/10-websocket-and-selection.html
    - 建立连接 → 接收消息 → 处理 → 发送消息 → 等下一条
    - accept / receive_text / send_json / close：本例的基本操作
    - 客户端可反复查询；服务端也可主动推送消息
    - 每条业务消息自己约定字段和成功、失败含义
    - 本例顺序处理消息；双向连接不自动让业务并发
  - 按需求选一种
    - 只查一次欠款 → 普通 HTTP
    - 发起一批后，只需服务端逐步给进度 → SSE
    - 需要保持连接、双方反复发送业务消息 → WebSocket
    - 模型流式输出是内容逐步产生；可以用 SSE 或 WebSocket 承载
  - 三个容易混淆的结束动作
    - 关闭连接：结束这条通信通道
    - 取消任务：请求停止某项异步工作
    - 重新连接：新建通道；任务与消息恢复需要另行设计
    - 关网页或重连，不自动证明远端业务已取消或恢复
  - 在统一例子里观察
    - 教材：http://127.0.0.1:8765/01-python-api/00-one-example.html#extensions
    - 同一个 book.query 负责查金额
    - 普通 HTTP：[S3]；SSE：[S5]；WebSocket：[S6]
    - 业务没换，主要变化是结果与消息怎样收发
